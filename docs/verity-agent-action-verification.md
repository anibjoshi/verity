# Agent-Action Verification: Threat Landscape, Defense Insufficiency, and the Systems-Security Precedent for Verity

## TL;DR

- **The uncontested gap is real and the precedent is decisive.** Every current agent defense class — input delimiters, detection suites, sandboxing, approval gates, model-based judges — degrades *toward* failure under adversarial pressure (independent red-teaming bypassed 12 recent defenses with attack success rate >90% for most; AgentDojo's own detector defense still leaks 8% of attacks). A deterministic, model-independent, pre-execution per-action verifier is exactly the "reference monitor" that decades of systems security (seccomp, SELinux, capabilities, seL4, AWS Zelkova) proved is the only thing that holds under attack. Verity's thesis is sound; the open question is *scope*, not validity.
- **The single biggest lesson is a cautionary one: SELinux was disabled across the industry not because it failed to enforce, but because its policy was unauthorable.** Verity's hardest problem is not the verifier — it is getting precise per-user policy from people who will never write one. The history says: ship a non-negotiable catastrophe floor (always-on, like seccomp), then learn the per-user layer from observed behavior and corrections (AppArmor's complain mode, audit2allow), and *never* surface noisy denials that tempt the operator to "setenforce 0."
- **Scope discipline is the whole game.** The honest disanalogy: syscalls are a closed, finite, semantically-stable set; agent actions are open-ended and semantic. Deterministic policy scales beautifully to a *crisp catastrophe-floor subset* (shell exec, secret-file reads, self-modification, exfiltration channels, irreversible/financial actions) and degrades to coin-flipping on open semantic judgment. Verity should claim the floor with provable guarantees (the AWS Zelkova model: invisible solver, surfaced verdict) and explicitly cede subjective/reversible judgment to model-based layers.

## Key Findings

1. **Prompt injection is unsolved and structurally unsolvable at the model layer.** Frontier models show 43–59% attack success rates to basic injection; independent adaptive attacks bypass 12 published defenses with attack success rate >90% for most. OpenAI's December 22, 2025 blog post states verbatim that "Prompt injection, much like scams and social engineering on the web, is unlikely to ever be fully 'solved'," and OpenAI CISO Dane Stuckey called it "a frontier, unsolved security problem." This is the load-bearing fact: if the model can be turned, the only durable boundary is one the model does not sit inside.
2. **The dangerous actions cluster tightly and map to a definable catastrophe floor.** Documented incidents converge on: arbitrary shell/command execution, secret-file reads (/etc/passwd, SSH keys, .env), self-modification / skill & MCP-config injection (persistence), and exfiltration channels (outbound HTTP, email, PR creation). The "lethal trifecta" (private data + untrusted content + external communication) is the structural precondition; the catastrophe floor is the set of actions whose combination makes the trifecta lethal.
3. **Incidents cluster on system/code-access, not consumer-lifestyle.** The 2025–26 incident record (CVE-2025-59536 Claude Code RCE via project files, CVE-2025-49596 MCP Inspector RCE, CVE-2025-6514 mcp-remote command injection, ClawHavoc's 1,184 poisoned skills, OX Security's 10-CVE MCP STDIO RCE cluster) is dominated by code-execution and supply-chain paths. This confirms system/code-access as the lead use case.
4. **Detection is structurally weaker than verification for irreversible actions** — a false negative in a detector is an executed irreversible action, whereas a deterministic pre-execution gate fails closed.
5. **Input-side defense does not remove the need for action-side verification.** Even CaMeL — the strongest data/instruction separation — enforces capabilities *at tool-call time*. The privileged-LLM pattern *assumes a deterministic enforcement layer exists*; Verity is that layer.
6. **The productization pattern is settled by AWS Zelkova:** keep the SMT solver invisible, surface only the verdict, eliminate the need for users to write specifications, and ask the security question on their behalf. This is precisely Verity's "compile policy from intent at authoring time, return a verdict at runtime" design.
7. **Frontier labs have independently converged on Verity's architecture.** Google's published agent-security approach explicitly advocates a two-layer model: deterministic runtime policy enforcement (Layer 1) plus reasoning-based defenses (Layer 2), and states the reasoning layer is "inadequate, on their own, for scenarios demanding absolute safety guarantees." Meta's "Agents Rule of Two" and Anthropic/Redwood control research point the same direction.

## Details

### 1. The agent-harness threat taxonomy (the documented present)

**Dominant attack classes, ranked by documented frequency/severity:**

1. **Prompt injection (direct + indirect).** OWASP ranks it LLM01 — the top LLM risk — and it sits beneath nearly every agent compromise. Greshake et al. (arXiv:2302.12173, "Not what you've signed up for") introduced indirect prompt injection: retrieved content acts as "arbitrary code" because LLM-integrated apps "blur the line between data and instructions." Measured attack success rates on frontier models: GPT-3.5-Turbo 47%, GPT-4o 43%, GPT-4o-mini 58%, Llama 3 59% (PromptShield benchmark, arXiv:2501.15145).
2. **Exec / allowlist bypass → RCE.** The mechanism is lexical: command allowlists are evaded via line continuation, busybox multiplexing, and GNU option abbreviation. This is the agent-era recurrence of the classic shell-metacharacter injection problem.
3. **Supply-chain / skill injection.** Skill-Inject (arXiv:2602.20156) found frontier models executed malicious skill-file payloads up to 80% of the time across 202 injection-task pairs. Snyk's ToxicSkills research (Feb 2026) scanned 3,984 skills from the ClawHub marketplace and found 36% contained prompt-injection techniques; 36.82% (1,467 skills) had at least one security flaw; 534 skills (13.4%) contained at least one critical-level security issue; and 76 confirmed active malicious payloads were found, 8 of them still live at publication. Snyk's finding: "Among confirmed malicious skills, 100% combined malicious code payloads with prompt injection." Antiy CERT's ClawHavoc documented 1,184 poisoned skills. The distinctive danger: a malicious skill *inherits the full permission set of the agent* and persists across removal because the directive "had always been part of its configuration."
4. **Data exfiltration.** The terminal stage of the lethal trifecta — outbound HTTP, image-URL parameters, email forwarding, PR creation. Real incidents: Writer.com (invisible-image URL exfiltration), GitLab Duo, the GitHub MCP exploit (one tool mixing all three trifecta properties).
5. **Privilege escalation / confused deputy.** The agent is tricked into using its *legitimate* privileges on the attacker's behalf — the single most important failure mode for Verity to reason about (see §9).
6. **Cross-layer composition.** Palo Alto Unit 42's "AI Agents Are Here. So Are the Threats." (May 2025) built two functionally identical applications on CrewAI and AutoGen, presented nine concrete attack scenarios (information leakage, credential theft, tool exploitation, remote code execution), and concluded that "most vulnerabilities and attack vectors are largely framework-agnostic" — the bugs are architectural, not framework-specific.

**The dangerous actions (raw material for the catastrophe floor):** arbitrary shell execution; reads of secret files (/etc/passwd, SSH keys, .env); writes to skill/MCP-config/persistent-memory locations (self-modification); outbound network/communication primitives; irreversible or financial state changes.

**Where incidents cluster:** overwhelmingly system/code-access (RCE, secret theft, supply chain), not consumer-lifestyle (smart home, payments, messaging). This is decisive for use-case priority.

### 2. Why every current defense class is insufficient

| Defense | Catches | Misses | Documented bypass |
|---|---|---|---|
| **Structural delimiters / spotlighting** | Naive injection that respects delimiters | Anything that reasons around the boundary | Hierarchical guardrails reduce ASR to ~23%, not zero (arXiv:2511.15759); does not verify tool calls at all |
| **Detection-only suites** | Known/obvious patterns | Novel & semantically-camouflaged attacks | Defers pre-execution action verification entirely; "99% is a failing grade in application security" (Willison) |
| **Sandboxing (gVisor, containers, workspaceOnly)** | Kernel/host-level escape | Authorized actions *within* the sandbox (the confused deputy); exfiltration via permitted channels | Sandbox limits blast radius, doesn't decide whether *this* action is allowed for *this* user |
| **Approval gates / blocklists** | Explicitly enumerated bad actions | Everything not enumerated; alert fatigue | OpenAI Operator: confirmations + watch mode + injection detector (99% recall/90% precision on 77 attempts) — attackers still succeeded 23% of the time across 31 scenarios |
| **Regex / lexical allowlists** | Exact string matches | Equivalent reformulations | Line continuation, busybox, option abbreviation |
| **LLM-as-judge / model approval** | Some subjective risk | Adversarial inputs (same model, same jailbreak) | "Non-deterministic and cannot provide absolute guarantees" (Google); LLM auto-approval flagged as a vulnerability in the Hermes audit |

**The decisive quantitative finding:** the joint OpenAI/Anthropic/Google DeepMind paper "The Attacker Moves Second" (arXiv:2510.09023) reports that systematic optimization (gradient descent, RL, random search, human-guided exploration) "bypass[ed] 12 recent defenses … with attack success rate above 90% for most; importantly, the majority of defenses originally reported near-zero attack success rates." Defenses that look perfect in their own papers collapse under adaptive attack. This is the empirical heart of the case for a *deterministic* boundary: only a boundary that does not depend on model judgment is immune to "the attacker moves second."

**Why detection < pre-execution verification for irreversible actions:** detection is necessarily probabilistic and after-the-fact relative to the decision; for an irreversible action (wire transfer, secret exfiltration, file deletion) a false negative *is* the catastrophe. Pre-execution verification fails closed: no verdict, no action.

**Why input-side defense doesn't remove action-side need:** separating data from instructions reduces the *probability the agent is deceived*; it does not constrain *what a deceived-or-buggy agent can do*. CaMeL itself enforces capabilities at tool-call time — i.e., it ends in action-side verification. Input-side and action-side are complementary, not substitutes.

### 3. Systems-security precedent — the goldmine

| System | Policy model | Enforcement point (reference monitor) | Adoption verdict |
|---|---|---|---|
| **seccomp / seccomp-bpf** | Syscall allowlist + arg filtering via BPF | Between syscall entry and handler dispatch; "if the filter says no, the handler never executes" | **Invisible infrastructure** — in every Chrome renderer, OpenSSH, container runtime |
| **SELinux** | Mandatory type-enforcement labels; deny-by-default | LSM hooks in kernel | **Widely disabled** (`setenforce 0`) due to authoring crisis |
| **AppArmor** | Path-based MAC profiles | LSM hooks | Moderately adopted; **survived because of learning mode** |
| **Capability security (Capsicum, seL4, EROS)** | Unforgeable tokens bundling designation + authority; no ambient authority | Kernel capability checks | Capsicum shipped in FreeBSD 9+; broad adoption limited by programmer effort |
| **LSM framework** | Pluggable reference-monitor hooks | Kernel mediation points | Invisible infrastructure |
| **Chrome site isolation + seccomp** | Two-layer: semantics (setuid) + attack-surface reduction (seccomp) | Process boundary | Invisible infrastructure |
| **eBPF runtime security (Falco, Tetragon)** | Rules over kernel events | eBPF programs at kernel hooks | Growing; detection-leaning |
| **gVisor / Firecracker** | Reimplemented/minimized kernel surface | User-space kernel / minimal VMM | Invisible infrastructure (container isolation) |

**The reference-monitor concept is the through-line:** a *complete, tamper-proof, verifiable* mediation point that every action must pass. seccomp's design even **eliminates TOCTOU by construction** — the Linux kernel documentation states "BPF makes it impossible for users of seccomp to fall prey to time-of-check-time-of-use (TOCTOU) attacks." This is a direct design lesson: Verity must evaluate against immutable, fully-resolved action parameters, not a description the agent can mutate after the verdict.

**What made systems adoptable:** they became *invisible* (no user authoring per-use), asked the security question *on the user's behalf*, and operated on a *bounded, crisp* action surface. seccomp didn't ask users to enumerate syscalls — Chrome shipped the profile.

**Where the analogy BREAKS (state this loudly):** syscalls are a **closed, finite, semantically-stable set** (a few hundred numbered entries; `write(fd, buf, n)` means the same thing forever). Agent actions are **open-ended and semantic** — "send an email," "run this command," "edit this file" range over an unbounded space, and the *meaning* of an action (is this exfiltration? is this a legitimate backup?) is context-dependent. seccomp can allowlist syscall 257; Verity cannot allowlist "all safe shell commands" because the set is infinite and adversarially extensible (the lexical-bypass problem). **Conclusion: deterministic policy scales to the catastrophe-floor subset where actions resolve to crisp, checkable predicates (this file path is a secret; this destination is off-allowlist; this action is irreversible/financial), and does not scale to open semantic judgment.** Verity must architect around the floor, not pretend to cover the whole action space deterministically.

### 4. The policy-authoring usability problem (the cautionary core)

**SELinux's authoring crisis is the most important precedent for Verity.** The precise usability failure: fine-grained type enforcement requires authoring/maintaining labels and allow-rules for every subject-object interaction; when something breaks, the *path of least resistance is `setenforce 0`* (disable enforcement) rather than diagnose-and-write-policy. The mechanism is **noise → disablement**: a security control that produces frequent, hard-to-resolve denials gets turned off wholesale, trading "a solved security problem for a persistent vulnerability." SELinux's own ecosystem built `audit2allow`, `audit2why`, `setroubleshoot`/`sealert` precisely to fight this — i.e., the tooling history is one long attempt to make policy authorable after the fact.

**What actually worked — AppArmor's learning model:** `aa-genprof` / `aa-logprof` run a profile in **complain mode** (violations logged, not blocked), the operator exercises the application, and the tool generates rules from observed behavior, iterating until "zero complain-mode log entries," then flips to **enforce mode**. This is *audit-to-policy*: derive least-privilege from observation rather than asking the human to specify it up front. The caution attached: `aa-easyprof` templates "may create a profile that is less restricted" — auto-generation trades precision for tractability.

**For Verity (this IS the personalization problem):**
- **Catastrophe-floor + learned-from-corrections beats ask-the-user-to-specify.** Nobody will author a per-user agent policy, exactly as nobody hand-writes SELinux TE rules. Ship the floor always-on (seccomp model); learn the per-user allowances from observed behavior and explicit corrections (AppArmor complain-mode model).
- **The analog of `setenforce 0` that Verity must avoid:** the user disabling the verifier (or routing around the harness) because it blocks too many legitimate actions. **This makes false-positive/noise budget the primary product metric, above coverage.** A verifier that is 99% strict but noisy gets disabled and protects no one; a verifier that gates only the crisp catastrophe floor and otherwise stays silent survives. The floor must be things a reasonable user would *never* want done silently — so a denial there reads as obviously correct, never as friction.

### 5. Deterministic & formal verification that succeeded in production

- **AWS Zelkova → IAM Access Analyzer** is the closest production analog and the productization template. Zelkova translates IAM/S3 policies into SMT formulas and uses a portfolio of SMT solvers (Z3, CVC4, cvc5) to make *universal* statements ("there is no public access to this bucket"). Per Amazon Science's "A Billion SMT Queries a Day" (CAV 2022, Rungta et al.), Zelkova grew "from a thousand SMT invocations daily to an unprecedented billion SMT calls in a span of five years," and cvc5 now powers "approximately one billion automated-reasoning checks across AWS every day," in hundreds of milliseconds to tens of seconds (it solves a PSPACE-complete problem). **The adoption lessons are explicit and directly transferable:** (1) *"eliminating the need for specifications"*; (2) *domain-specific abstractions* — "do one thing and do it really well" — building the one-click IAM Access Analyzer on top of raw Zelkova; (3) the solver is invisible — users "think about its value to them," not the math. This is *exactly* Verity's "LLM+SMT compiles policy from intent at authoring time; runtime returns only a verdict."
- **seL4** — first OS kernel with a machine-checked functional-correctness proof (8,700 LOC C, ~9–18k SLOC TCB depending on architecture), down to binary, including information-flow security proofs. Adoption: high-assurance/defense (DARPA PROVERS/INSPECTA), not general-purpose. Lesson: formal verification reaches production where the **scope is bounded and the stakes justify the cost**.
- **Certora** — SMT-based smart-contract verification. Per Certora's Feb 24, 2025 announcement, the Certora Prover "has secured more than $100 billion in total value locked (TVL)" with "over 70,000 verification rules"; its 2025 Year-in-Review (Jan 2026) reports it "helped secure $196.5 billion in total value locked … and prevented more than 720 vulnerabilities from reaching production," with 14 of the top 20 DeFi protocols as clients (Aave, MakerDAO, Uniswap, Lido, EigenLayer). Adoptable because the EVM's *deterministic, bounded execution* makes formal methods tractable — and because a single bug means catastrophic, irreversible loss. Lesson: deterministic + irreversible + high-stakes = the sweet spot for formal verification, *which is exactly the agent catastrophe-floor profile.*
- **CFI / IFC** — reached production narrowly (CFI in compilers/OS; IFC mostly research) because the property is crisp.

**Recurring reason things stayed academic:** they required users to write specifications, or operated on unbounded/ill-defined scope. **Productization pattern for Verity:** invisible solver, surfaced verdict, eliminate specifications via intent-compilation, bound the scope to crisp predicates, escalate the rest to humans/model layers.

### 6. Prompt-injection & tool-use safety research

- **What actually constrains actions vs. reduces deception probability:** Training-based defenses, spotlighting, and instruction hierarchy *reduce deception probability* (Anthropic self-reported 88% injection blocking on Claude 3.7 — a vendor figure that independent adaptive testing would lower). Only **capability/IFC enforcement at tool-call time** (CaMeL) and **deterministic policy gates** actually *constrain what the agent can do*.
- **CaMeL (arXiv:2503.18813, Google/DeepMind/ETH)** is the key complement: it formalizes Willison's dual-LLM pattern (privileged LLM plans; quarantined LLM touches untrusted data, no tools), tracks data/control flow in a custom interpreter, and **enforces capabilities and security policies when tools are called**. On AgentDojo it solves 77% of tasks with provable security vs. 84% undefended — and crucially, it "does not rely on model behavior." For several models it reduces successful attacks to zero (e.g., Gemini 2.5 Pro: 300 successful attacks without CaMeL → 0 with it). **CaMeL's own conclusion is Verity's thesis statement:** *"it is possible to design a system around an untrusted model that makes the whole system robust even if the model itself is not."*
- **Reliability ceiling of model-based guards:** "The Attacker Moves Second" (>90% bypass of 12 defenses) plus the 43–59% baseline ASRs establish that model-based guards have no adversarial floor. This *implies* a deterministic outer boundary for anything irreversible.
- **What Verity complements vs. competes with:** It **complements** the dual-LLM/CaMeL/privileged-LLM family (it is the deterministic enforcement layer those patterns assume), AI-control monitoring (Redwood's defer-to-trusted/resample protocols — which are probabilistic and benefit from a deterministic backstop on critical actions), and input-side spotlighting. It **competes with** detection-only suites and LLM-as-judge approval *for the specific job of gating crisp irreversible actions* — and should win there on the determinism argument.

### 7. Frontier-lab agent-safety priorities (lab relevance)

- **Google (verbatim):** "An Introduction to Google's Approach to AI Agent Security" (Díaz, Kern, Olive, 2025) advocates a hybrid of "traditional, deterministic security measures with dynamic, reasoning-based defenses." **Layer 1 is a runtime policy engine** that *intercepts every tool call* and evaluates it against rules keyed on "the action's inherent risk (Is it irreversible? Does it involve money?), the current context, and … the chain of previous actions (Did the agent recently process untrusted data?)" — allow, block, or require confirmation. **Layer 2 (reasoning-based) "cannot provide absolute guarantees … inadequate, on their own, for scenarios demanding absolute safety guarantees, especially involving critical or irreversible actions. They must work in concert with deterministic controls."** This is, almost line for line, Verity's pitch — and it means Verity is building the Layer-1 reference implementation that Google describes but treats as bespoke per-deployment. Google names the two core risks as **"rogue actions"** and **"sensitive data disclosure."**
- **Meta — "Agents Rule of Two" (Oct 31, 2025; NOT Anthropic, despite common mis-attribution):** until injection can be reliably refused, an agent session "must satisfy no more than two" of: (A) process untrustworthy input; (B) access sensitive systems/private data; (C) change state or communicate externally. If all three are needed, "the agent should not be permitted to operate autonomously … [and] at a minimum requires supervision." This is the lethal trifecta operationalized as policy — and *deciding when a session crosses the line is exactly a deterministic verification job.*
- **OpenAI (Operator / ChatGPT agent):** ships confirmations, watch mode, refusals, and an injection detector — explicitly framed as "speed bumps," with the company conceding (Dec 22, 2025) that injection is "unlikely to ever be fully 'solved'." The labs are publicly admitting the model-layer ceiling — which is Verity's opening.
- **Anthropic / Redwood:** AI-control work (defer-to-trusted, resampling, "defer on critical actions") found "deferring on critical actions is highly robust to even our strongest red team strategies" — independent confirmation that *gating the critical-action subset* is where robustness lives.

**Framing/vocabulary that makes Verity legible to labs:** "Layer-1 deterministic runtime policy enforcement" (Google), "reference monitor for agent actions," "the deterministic enforcement layer the privileged-LLM pattern assumes," "defer-on-critical-actions, made deterministic," and "operationalizing the Rule of Two / lethal trifecta at the tool-call boundary."

### 8. The discriminating boundary — deterministic vs. model judgment

| Use deterministic verification when… | Cede to model/LLM judgment when… |
|---|---|
| Adversarial setting (attacker controls inputs) | Non-adversarial, cooperative context |
| Action is irreversible (delete, send, transfer, exfiltrate) | Action is reversible / low-stakes |
| The predicate is crisp and checkable (path is a secret; destination off-allowlist; amount > threshold; action mutates skill/config) | The judgment is subjective/semantic (is this email *appropriately* worded? is this a *good* refactor?) |
| Catastrophe floor (the universal "never silently" set) | Personalized preference, taste, helpfulness |

**Verity's credibility is in the honesty of this line:** claim provable guarantees only for the crisp, irreversible, adversarial subset; explicitly and loudly cede the rest. Overclaiming deterministic coverage of open semantic judgment would repeat the SELinux over-reach (trying to label everything) and invite the same disablement.

### 9. Failure modes & disconfirming evidence

- **The confused deputy is Verity's most serious exposure.** The classic definition: a privileged program is "tricked by another program … into misusing its authority." This is *precisely* the agent attack — the agent has legitimate privileges; injection tricks it into using them for the attacker. **Capabilities mitigate confused deputy only by bundling designation + authority** (you act on the resource whose capability you were handed, not on an ambient name). **Critical transfer caveat: Verity does NOT automatically solve confused deputy.** If it authorizes actions by *type* ("agent may send email") without binding *which* data flows to *which* destination *under which provenance*, it is still confusable. The defense must be provenance/taint-aware (CaMeL's contribution) — gate on "tainted execution path attempting exfiltration," per Willison's taint-tracking proposal — not merely on action type. The "Visual Confused Deputy" paper (arXiv:2603.14707) shows an 8-line pixel-swap inducing privilege escalation in computer-use agents, indistinguishable from a benign misclick — a reminder that the verifier must act on ground-truth action parameters, not the agent's (manipulable) perception.
- **TOCTOU / reference-monitor gaps.** If Verity verifies a described action and the agent (or a race) substitutes a different one before execution, the verdict is void. seccomp solved this by mediating at the syscall instruction itself. **Lesson: Verity must verify the fully-resolved, immutable action at the execution instant, in the same critical section as the dispatch** — no gap between check and use.
- **SELinux disablement** (covered in §4) — the authoring-noise → disablement failure. Verity *is* exposed to this; it is the #1 product risk.
- **Sandbox escapes & seccomp-filter bypasses** show that *any* boundary with implementation bugs can be escaped (e.g., seccomp + ptrace escape if ptrace isn't also blocked — the kernel docs warn "seccomp-based sandboxes MUST NOT allow use of ptrace … without extreme care"). Lesson: the verifier's own attack surface and tamper-resistance (it must not be jailbreakable along with the agent — Verity's core claim) must be ruthlessly minimized, à la seL4's small TCB.
- **Capability adoption failures** show that even correct mechanisms stall on programmer/authoring friction — reinforcing the "invisible + learned, never hand-authored" mandate.

## Recommendations

**Decision 1 — Catastrophe floor (concrete candidate list, always-on, deny-or-confirm by default):**
1. Arbitrary shell / command execution (and any exec primitive) — gate on a *semantic* allowlist of resolved commands, not lexical strings, to defeat busybox/option-abbreviation bypass.
2. Reads of secret material: /etc/passwd, SSH private keys, cloud-credential files, .env, token stores.
3. Writes/mutations to self: skill files, MCP/agent config, persistent memory, system prompt, autostart locations (the persistence/self-modification class).
4. Outbound exfiltration channels when on a tainted execution path: arbitrary outbound HTTP, email/chat send, PR/issue creation, clipboard/image-URL side channels.
5. Irreversible or financial actions above threshold: payments/transfers, deletions, mass mutations, external publishing.
6. Network egress to non-allowlisted destinations.

The unifying rule, drawn from Meta's Rule of Two and the lethal trifecta: **block (or force human confirmation for) any action that combines untrusted-content provenance + sensitive access + external/irreversible effect in one tainted path.** Floor membership criterion: *a reasonable user would never want this done silently* — so denials read as obviously correct.

**Decision 2 — Use-case priority:** **System/code-access actions are the lead, decisively.** The incident record (RCE CVEs, secret theft, ClawHavoc skill poisoning) clusters there; consumer-lifestyle is secondary. Build and benchmark on coding-agent / shell / file / MCP surfaces first.

**Decision 3 — Interception architecture:** **Both, but the deterministic action-side gate is Verity's lane.** Place the reference monitor at the tool-execution step (Google's Layer 1), mediating the fully-resolved action in the same critical section as dispatch (seccomp's TOCTOU-free placement). Consume provenance/taint metadata from the input side (CaMeL-style) so the gate can reason about confused-deputy/exfiltration paths. Map explicitly to LSM-hook / reference-monitor placement in your security narrative.

**Decision 4 — Authoring/personalization:** **Catastrophe-floor-always-on + learn-the-rest-from-behavior-and-corrections.** Never ask non-experts to author policy (the SELinux failure). Ship the floor like seccomp (invisible, default); generate the per-user layer like AppArmor complain mode (observe → propose → confirm → enforce) with an audit2allow-style "approve this and remember it" correction loop. **Optimize relentlessly against false-positive noise** — it is the `setenforce 0` trigger and the top product risk.

**Decision 5 — Positioning:** "The deterministic, model-independent reference monitor for agent actions — the Layer-1 runtime policy enforcement that Google says reasoning-based defenses 'must work in concert with,' and the enforcement layer the privileged-LLM/CaMeL pattern assumes exists." Differentiate crisply: input-delimiters reduce deception probability (we constrain capability); detection is after-the-fact and probabilistic (we are pre-execution and fail-closed); sandboxing limits blast radius (we decide per-action, per-user authorization); LLM-judges share the agent's jailbreak (we are outside the model). Borrow AWS Zelkova's proof: invisible solver, surfaced verdict, no specifications required.

**Decision 6 — Lab relevance:** Frame the work in lab vocabulary: Google's two-layer model (you are the reference Layer 1), Meta's Rule of Two (you operationalize it at the tool boundary), Redwood's "defer on critical actions, made deterministic," and OpenAI's admission that injection won't be "solved" at the model layer. Benchmark on AgentDojo (97 tasks, 629 security cases) and report provable-security coverage of your floor the way CaMeL reports its 77%.

**Top risks and cheapest experiments to de-risk each:**
- *Risk: authoring-noise → disablement (the `setenforce 0` failure).* **Cheapest experiment:** instrument a coding-agent harness, run real workflows, measure false-positive denials per session on your floor. If the floor is well-scoped, this should approach zero. Threshold to change course: if floor denials exceed ~1 false positive per several sessions, the floor is too broad.
- *Risk: confused deputy / type-only authorization.* **Experiment:** red-team with provenance-blind vs. provenance-aware policies on AgentDojo exfiltration tasks; show taint-aware gating closes attacks that type-only gating misses.
- *Risk: lexical/semantic bypass of command gating.* **Experiment:** replay the allowlist-bypass corpus (line continuation, busybox, option abbreviation) against a semantic-resolution gate; target 0% bypass.
- *Risk: TOCTOU between verdict and dispatch.* **Experiment:** adversarial action-substitution test; verify the gate operates on immutable resolved parameters.
- *Risk: scope overreach (deterministic claims on semantic judgment).* **Experiment:** classify a sample of real agent actions as "crisp-floor" vs. "semantic"; confirm the floor is a small, stable, high-agreement set — if it isn't, narrow it.

## The one-question test

**The single most important lesson from decades of constraining powerful untrusted execution, for Verity, is that the verifier will only ever protect anyone if it is never disabled — and SELinux proves controls get disabled not when they fail to enforce but when their policy is unauthorable and their denials are noisy — because a deterministic boundary's security value is exactly zero the moment an operator types `setenforce 0`, so Verity must win on authorability and silence (a tight, always-on catastrophe floor whose denials are self-evidently correct, plus a per-user layer learned from behavior, never hand-written) before it wins on coverage.**

## Caveats

- **Verity, OpenClaw, Hermes (#7826), "clawsec," and arXiv 2603.27517 are taken as given premises** from the brief; I did not independently verify those specific identifiers and treated them as (likely pseudonymized) stand-ins. The cited public artifacts (Greshake 2302.12173, CaMeL 2503.18813, AgentDojo 2406.13352, "The Attacker Moves Second" 2510.09023, and the seccomp/SELinux/AppArmor/Capsicum/seL4/Zelkova/Certora and OpenAI/Google/Meta publications) are real and verified.
- **Attribution correction:** "Agents Rule of Two" is a **Meta AI** framework (Oct 31, 2025), not Anthropic. The Anthropic-co-authored November 2025 work is the separate "The Attacker Moves Second" paper.
- Vendor-reported defense numbers (e.g., Anthropic's 88% injection blocking, OpenAI's 99%/90% detector) are self-reported on internal benchmarks; independent adaptive testing consistently lowers such figures. Treat them as upper bounds.
- Some 2026-dated incident write-ups (ClawHavoc, OX Security MCP cluster, Check Point Claude Code CVEs, Snyk ToxicSkills) come from vendor security blogs and research notes; the CVE identifiers and core facts are corroborated across multiple sources, but individual figures (e.g., exact poisoned-skill counts) vary by source.
- Per-model AgentDojo metrics circulating in secondary aggregators are lower-confidence; the paper's own headline numbers (<66% undefended utility, <25% best-agent ASR, 8% with detector) are the safe citations.
